# Асинхронный процессинг платежей

Сервис принимает платежи по HTTP. Воркер эмулирует работу платёжного шлюза и отправляет результат на webhook клиента.

## Запуск

```sh
docker compose up --build -d
```

Compose поднимает PostgreSQL, RabbitMQ и приложение. Alembic применяет миграции перед запуском. FastAPI слушает `127.0.0.1:8000`, а его lifespan запускает RabbitMQ-консьюмер FastStream и публикацию outbox. Для локального запуска ключ по умолчанию `local-payment-key`. Переопределить его можно через `API_KEY` в окружении или `.env`.

## API

Создать платёж:

```sh
curl -i http://127.0.0.1:8000/api/v1/payments \
  -H 'X-API-Key: local-payment-key' \
  -H 'Idempotency-Key: order-123' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"19.50","currency":"EUR","description":"Order 123","metadata":{"order_id":123},"webhook_url":"https://example.com/payments"}'
```

Подставьте URL получателя, доступного из контейнера `api`. Поддерживаются HTTP и HTTPS. Пример ответа `202 Accepted`:

```json
{"payment_id":"759cb596-67d9-47e1-9eb1-35215b686ba3","status":"pending","created_at":"2026-11-19T10:00:00Z"}
```

Получить актуальные данные о платеже:

```sh
curl -i http://127.0.0.1:8000/api/v1/payments/759cb596-67d9-47e1-9eb1-35215b686ba3 \
  -H 'X-API-Key: local-payment-key'
```

Сумма передаётся десятичной строкой с точностью до двух знаков после точки. Валюты `RUB`, `USD` и `EUR`. Повтор POST с тем же ключом и теми же данными вернёт исходный `202`, даже если платёж уже завершён. Повтор с изменёнными данными вернёт `409 Conflict`.

## Обработка и доставка

- API сохраняет платёж и запись в `outbox` одной транзакцией. Воркер читает неопубликованные записи с `FOR UPDATE SKIP LOCKED` и отмечает их опубликованными после подтверждения RabbitMQ.
- Единственный обработчик `payments.new` эмулирует обработку за 2–5 секунд с вероятностью успеха 90%. Статус `succeeded` или `failed` записывается в PostgreSQL до отправки webhook.
- Webhook получает JSON с `event_id`, `payment_id`, `status` и `processed_at`. HTTP-клиент использует `base-client` и подтверждает доставку по любому статусу `2xx`. Обработчик резервирует каждую попытку в БД до отправки. Лимит в три попытки действует и после перезапуска, даже если процесс завершился между резервированием и отправкой. Между ошибками отправки в рамках одной обработки воркер ждёт 1 и 2 секунды. Когда попытки закончились, RabbitMQ отправляет событие через `payments.dlx` в `payments.dead`.
- При повторной доставке сообщения воркер использует сохранённый результат платежа. Если получатель принял webhook, а воркер завершился до записи подтверждения в БД, webhook может прийти повторно. Получатель может распознать повтор по `event_id`.

Имена очередей, пулы соединений, таймауты и задержки повторных попыток задаются в `payment_processing/settings.py`. После трёх локальных попыток при временном сбое PostgreSQL воркер возвращает событие в RabbitMQ с паузой, пока БД не восстановится. Временные сбои при публикации outbox повторяются с задержкой до 30 секунд. Если публикация outbox остановилась из-за необработанной ошибки, API отвечает `503` на создание платежей. При недоступности RabbitMQ приложение завершает запуск с ошибкой.

## Проверки

```sh
just lint
just test
```

Для `just lint` нужны Python 3.15 и uv. `just test` запускает интеграционные тесты в отдельном Docker Compose-проекте с PostgreSQL и RabbitMQ и удаляет его после прогона. GitHub Actions запускает обе команды на push и pull request.
